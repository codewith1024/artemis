# 凌晨 00:05 定时采集：就绪审计与拦路虎修复

## 结论

对着 00:05 的 launchd 轮次（`qnh-daily-incremental-capture`，cron `5 0 * * *`）做了逐项
审计。**三个会让整轮白跑的拦路虎已修**（都改在代码里，不动数据库）：

1. **多 SKU 产物入库被拒** → 整轮采完（十几小时）在提交那一步失败。
2. **观测终态产物入库被拒** → 猫粮/猫零食的渠道行缺失会让快照进不去库。
3. **平台计数差（猫粮 52/51、猫零食 44/43）无放行证明** → 这两片 20 次重试后仍失败，
   整轮跟着失败。

**没有连接或修改业务数据库**（验证用假库，`db_connections_opened=0`），没有 DDL、回填、
dry-run 入库或正式提交。

## 审计基线：上一轮（20261020）到底是怎么成功的

| 事实 | 数值 | 含义 |
|---|---:|---|
| 分片终态 | 184/184 success | 分片本身能跑完 |
| 平台计数差 | 2 片（猫粮 51/52、猫零食 43/44） | 靠当时那条 set 口径的覆盖证明放行 |
| 多 SKU 分片 | 0 | 当时扫描器还认不出多 SKU 卡 |
| 行状态 | 携带 8,419 / 实访 1,836 | 82% 的商品跳过了详情页（携带基线） |
| 耗时 | 23:24 → 02:08（约 2h44m） | 短，因为大部分没实访 |

**两个结论**：上一轮的「成功」依赖两条现在已经不成立的捷径（set 口径的覆盖证明、
携带基线）；而多 SKU 与渠道行缺失这两件事，上一轮的扫描器根本看不见。

## 拦路虎一：多 SKU 产物入库被拒

`qnh_load_db._reject_multi_sku` 见到 `scope.sku_mode=sidecar_v1` 就拒。而新扫描器会
产出多 SKU 卡（真机猫粮 10 张、猫零食 2 张）→ 整轮采完在提交那一步失败。

**已修**：多 SKU 卡片按 sidecar 的子行逐 SKU 成行。

- 卡片行本身不入库（它没有 SKU 身份，入库就是拿代表 SKU 冒充整张卡）。
- 每个 SKU 事实行带 `sku_count`（该 SPU 的 SKU 数）与 `has_multi_spec`——这两列本来
  就在表里，只是从来没人写。
- 快照的 `captured_spu_count`（卡片）与 `captured_sku_count`（SKU）分开记。
- 加载器与校验器共用同一份展开（`C.fact_sources`），两处各判各的校验就成了自证。
- 直接 CSV 模式没有 sidecar 就没法展开 → 仍然拒绝（消息写明原因）。

**没有 DDL**：表里早有 `sku_count` / `has_multi_spec` 两列（"该 SPU 下 SKU 数"、
"是否多规格（卡片按钮是「选规格」）"），schema 本来就是照多 SKU 设计的。

## 拦路虎二：观测终态产物入库被拒

渠道行缺失（某 SKU 在某渠道没有行）只能记「未知」，而带「未知」的产物是观测终态
（`observed_with_exceptions`），入库入口此前一律拒。

**已修**（用户已授权动 DB 契约）：未知可以入库，但快照要如实标不完整。

| 位置 | 未知渠道格的落库值 |
|---|---|
| `sale_status` | `'unknown'`（表注释本来就写着 available / out_of_stock / unknown） |
| `listing_status` | NULL（SKU 级上架状态不可推断，不写已下架/未上线） |
| `front_display_price_amount` / `stock_quantity` | NULL（不写 0） |
| `store_snapshot.status` | `'partial'`（业务不完整这件事写在快照上） |
| `store_snapshot.error_message` | 逐条记观测例外 |

同一张卡的其他渠道照常写真值（例如真机猫粮 40g 那个 SKU：美团闪购 2.8 元/售罄，
京东到家「未知」）。**没有 DDL**：表里 `sale_status` 的 `'unknown'` 就是为此准备的。

严格门禁仍然拒绝观测终态产物（「不完整」不被掩盖），只是不再挡住入库。

## 拦路虎三：平台计数差没有成立的放行证明

平台标题数 52、可见卡数 51：上一轮靠「列表解析出的卡片集合 == 采到的卡片集合」放行，
那是 set 口径——同名同规格的两张卡会塌成一张，set 相等不等于张数相等，真漏抓会跟着
被藏掉。上一轮把它收紧成「一律失败」之后，猫粮/猫零食这两片就永远过不了。

**已修**：换成成立的三条证明（扫描器的 `coverage_snapshot` 给出，门禁核对）。

1. `list_exhausted`：列表读到了末尾（App 的读尽标记）。
2. `cards_match`：滚动时解析到的身份集合 == 采集行里的身份集合。
3. `rows_have_distinct_identities`：采集行里没有两行共享身份——否则行数不能当卡数用。

三条都成立，差额才是「App 侧多计」（它把没渲染出来的商品也算进标题数），不是我们
漏抓；任一条不成立就是真漏，一律失败。**平台目标数不改写**（仍是 52/44）。

真机历史数据核对：猫粮 51 行的身份两两不同 → 证明成立 ✓。

## 每日轮次的两处配套改动

- `qnh_daily_run.py` 给分片器加 `--observe-exceptions`：渠道行缺失被如实记成「未知 +
  证据」，而不是让整片失败重采 20 次。
- 分片器的 `--observe-exceptions` 不再与 `--commit` 互斥（聚合是全店并集，落一份
  「带未知的快照」有意义）。**单类目的观测产物仍然只 capture-only**——那不是全店快照，
  入库会冒充门店快照。

## 验证

- 牵牛花专项 **410 passed / 8 skipped**；全仓单元测试 **2,904 passed / 3 failed /
  12 skipped**（3 项失败仍是既有模型提供商配置断言 `assert 'anthropic' == 'google'`）。
- **真机 20261021 猫粮产物跑通整条入库链路（假库）**：51 张卡 → 65 个 SKU → 195 条
  事实行；快照 status=partial；3 个已观察到的行缺失格记 unknown（listing_status 为
  空、价与库存为空），另 2 个「未上线」格照常记 not_online；72 条多 SKU 事实行带
  sku_count（2/3/4）；事务内逐字段校验 **20 passed / 0 failed**。
- **真机两片聚合产物同样跑通**：92 张卡 → 110 个 SKU → 330 条事实行，3 条类目行，
  校验 20/0。
- 新增 `tests/unit/test_qnh_multisku_ingest.py`（7 项）＋ 覆盖证明新口径 4 项。

## 仍然存在的风险（需要人知道，不是代码拦路虎）

1. **时长会明显变长**。携带基线已停用（携带行的详情是历史合成值，不是当日真值，
   入库必须是当日实访），所以 10,491 个商品要逐个实访详情页。上一轮 1,836 个实访用了
   约 2 小时 44 分（含分片开销），按同一单商品耗时折算，全量实访约 **7–9 小时**，
   再加观测模式的逐片列表预扫（184 片 × 约 25 秒 ≈ 1.3 小时）→ **约 9–11 小时**，
   仍在 12–16 小时的窗口内。跨日完成是允许的，但**第二天 00:05 的轮次会被全局锁挡住
   而顺延**。
2. **快照状态会是 partial**。只要有分片带观测例外（猫粮/猫零食几乎必然有渠道行缺失
   与平台计数差），聚合就是观测终态，入库后 `store_snapshot.status='partial'`。
   数据照常入库，未知格如实标 unknown——但下游若把 `partial` 当异常处理，需要先对齐
   这个口径。
3. **平台后台多计 1 的根因仍未知**。本地契约只诚实记录 UI 已观察事实：App 渲染 51 张卡、
   标题写 52。
4. **设备与网络**：手机 192.168.100.14:5555 在线、AC 供电中（stay-on 生效）、电量
   100%；整轮十几小时里 Wi-Fi 掉线仍可能发生，巡检会话按约定「通知用户恢复、不硬撞」。
5. 20261020 那一轮的 8,419 条携带行仍留在历史快照里（历史事实，不回改）。
