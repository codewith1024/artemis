# 门店商品价格快照库 建表说明（交 DBA）

版本：v1　日期：2026-09-29　附件：`retail_price_snapshot_schema.sql`（建表脚本，9 张表）

## 一、背景

我们在采集外卖平台（目前是美团）门店的商品和价格数据，用来和自有门店做比价、监控竞对价格和活动。

以前的美团采集表（`store_raw_data_snapshot`、`fact_store_spu_price_snapshot`、`fact_store_sku_price_snapshot`）在 qnh_data 里已经不存在，也没有可恢复的历史数据。这次在一个**新库**里重新建表：旧表的原有列全部保留，列名和含义不变，另外按新采集到的数据补了字段和配套表。

## 二、需要 DBA 做的事

### 1. 建库

| 项 | 要求 |
|---|---|
| 库名 | 建议 `retail_price_snapshot`，可以改，改了告诉我们 |
| 字符集 / 排序规则 | `utf8mb4` / `utf8mb4_0900_ai_ci` |
| MySQL 版本 | **8.0.16 及以上**（用到了 JSON 列、CHECK 约束、0900 排序规则） |
| 部署位置 | **建议和 qnh_data 放在同一个实例上（192.168.100.200）**，这样比价时能直接跨库关联 `qnh_data.goods_master_goods`、`qnh_data.data_store_info`。放不到同一个实例的话告诉我们，我们改成同步维表的方式 |
| 时区 | 业务时间都按北京时间写入 DATETIME 列，不依赖服务器时区；`created_at` 用 TIMESTAMP，建议实例 `time_zone='+08:00'` |
| sql_mode | 保持默认严格模式（`STRICT_TRANS_TABLES`）即可 |

```sql
CREATE DATABASE retail_price_snapshot
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

> 如果实例是 MySQL 5.7：把脚本里的 `utf8mb4_0900_ai_ci` 全部替换成 `utf8mb4_unicode_ci` 就能执行，但 5.7 不会校验 CHECK 约束（语法能过，约束不生效）。遇到这种情况请告诉我们，我们在程序里做校验。

脚本只有 `CREATE TABLE IF NOT EXISTS`，没有 DROP 和数据写入，可以重复执行。

### 4. 容量和保留策略（请 DBA 评估）

用目前已采到的数据推算（乐购达超市湖里店：实采 3,208 个 SPU、4,244 个 SKU；平台显示店内约 8,000 件商品）。单个商品的原始 JSON 中位数约 12 KB，P95 约 19 KB。

| 表 | 一家约 8,000 SPU 的门店，全量采一次 |
|---|---|
| `store_raw_data_snapshot`（原始 JSON） | 约 110 ~ 130 MB，占总量的 85% 以上 |
| `fact_store_sku_price_snapshot` | 约 1 万行，10 MB 左右 |
| `fact_store_spu_price_snapshot` | 约 8 千行，8 MB 左右 |
| 其余 6 张表 | 合计不到 5 MB |
| **合计（含索引，粗估）** | **约 150 MB / 店 / 次** |

按 2 家店、每天全量采一次算：一天约 0.3 GB，一年约 100 GB，大部分是原始 JSON。

建议：

1. **原始表 `store_raw_data_snapshot` 在线只保留最近 90 天**（约 25 GB），更早的数据按 `collected_at` 删除，删之前由我们导出成 JSONL 归档。事实表长期保留（一年 10 GB 左右）。
2. 原始表空间紧张的话，可以对 `store_raw_data_snapshot` 开 `ROW_FORMAT=COMPRESSED` 或页压缩，DBA 按实例情况决定。
3. 暂时不分区。以后需要按月分区的话，要把 `snapshot_hour` / `collected_at` 加进主键和唯一键，我们配合改。
4. 以后如果改成每小时采一次，数据量是上面的 24 倍，到时候提前和 DBA 确认。

## 三、表清单与关系

| # | 表名 | 类型 | 粒度（唯一键） | 说明 |
|---|---|---|---|---|
| 1 | `dim_store` | 维表 | 渠道 + 门店稳定编码 | 采集的门店清单（自有 / 竞对） |
| 2 | `dim_store_source_id` | 映射 | 渠道 + 平台门店 ID | 平台门店 ID → 稳定编码 |
| 3 | `map_source_sku_standard` | 映射 | 渠道 + 平台 SKU ID | 平台商品 → 自有商品主档的匹配结果 |
| 4 | `store_snapshot` | 采集版本 | 门店采集版本 ID | 一家店全量采一次 = 一行，含当时的门店指标和完整性统计 |
| 5 | `store_raw_data_snapshot` | 原始层（旧表扩展） | 版本 + 门店 + 记录哈希 | 接口返回的完整 JSON，不裁剪 |
| 6 | `fact_store_category_snapshot` | 事实 | 版本 + 类目 | 门店类目树、每个类目的商品数 |
| 7 | `fact_store_spu_category_rel` | 事实 | 版本 + 类目 + SPU | 商品挂在哪些类目、排第几、是不是广告位 |
| 8 | `fact_store_spu_price_snapshot` | 事实（旧表扩展） | 版本 + SPU | SPU 价格快照 |
| 9 | `fact_store_sku_price_snapshot` | 事实（旧表扩展） | 版本 + SPU + SKU | SKU 价格快照（主要的比价表） |

表之间的关联（逻辑关联，没有建外键）：

```
dim_store (channel_code, store_code)
   ├── dim_store_source_id.store_code
   └── store_snapshot.store_code
          └── store_snapshot_id ─┬── store_raw_data_snapshot
                                 ├── fact_store_category_snapshot
                                 ├── fact_store_spu_category_rel
                                 ├── fact_store_spu_price_snapshot
                                 └── fact_store_sku_price_snapshot
                                          └── (channel_code, source_sku_id) → map_source_sku_standard
                                                    └── standard_sku_id → qnh_data.goods_master_goods.sku
```

不建外键的原因：快照表写入量大，而且要按版本整批清理，外键会拖慢写入和删除。数据一致性由入库程序保证。

## 四、相对旧表的改动

### 旧表保留并扩展（原有列一个不少，类型不变）

| 旧表 | 主要改动 |
|---|---|
| `store_raw_data_snapshot` | ① `record_type` 增加 `store`（门店信息）。旧 CHECK 只允许 `product` / `category`，和列注释写的“product、category 或 other”对不上，现在统一成 `store / category / product / other` ② 新增 `batch_id`、`source_api`、`request_tag_id`、`page_index`，能追溯到具体是哪个接口、哪一页 ③ 新增按商品查历史的索引 |
| `fact_store_spu_price_snapshot` | ① 新增 `store_snapshot_id`，唯一键改为 `(store_snapshot_id, source_spu_id)`；旧唯一键的列保留成普通索引 ② 新增：二级类目、平台标准类目一~三级、活动价、会员价、活动 tag / 类型、月售、想买人数、卖点、主图、售卖状态、对应原始记录哈希等 |
| `fact_store_sku_price_snapshot` | ① 同上，唯一键改为 `(store_snapshot_id, source_spu_id, source_sku_id)` ② 新增：活动价、活动类型 / ID / 起止时间、优惠力度、闪购补贴价、会员价、包装费、活动库存、归一规格和净含量（便于按单位价比价）等 |

唯一键为什么改：旧的 `(batch_id, store_code, …)` 在同一个批次里重采同一家店时会冲突。改成按“门店采集版本”唯一，每次重采是一个新版本。

### 新增的表，以及为什么要加

| 新表 | 为什么需要 |
|---|---|
| `store_snapshot` | 旧设计里原始层用 `store_snapshot_id`、事实层用 `batch_id`，两者的对应关系没有落表。现在统一登记在这张表里，还记录采集定位（价格和可售范围会随收货地址变化）、门店当时的评分 / 起送价 / 配送费、平台声明商品数和实采数，用来判断采全了没有 |
| `dim_store` / `dim_store_source_id` | 美团 H5 的门店 ID（`poi_id_str`）会随登录用户和会话变化，同一家乐购达湖里店已经见到过 2 个不同的值，所以不能直接拿它当门店主键。这里用我们自己的稳定编码，平台 ID 通过映射表转换 |
| `fact_store_category_snapshot` | 旧表只有“主类目”一个字段，没有类目树，也没有每个类目的平台商品数，没法核对完整性 |
| `fact_store_spu_category_rel` | 实测约 10% 的 SPU 同时挂在 2~4 个类目下（比如既在“神价”又在“休闲食品”）。旧表的唯一键决定了一个 SPU 只能记一个类目，其他归属和排位就丢了 |
| `map_source_sku_standard` | 旧表的 `standard_*_id` / `match_status` 每个快照都要重新算一遍。匹配结果（包括人工复核）放到这里长期有效，入库时直接带出来 |

### 旧文件中的不一致（已处理，仅记录）

- 旧 README 写的表名是 `act_store_spu_price_snapshot` / `act_store_sku_price_snapshot`，旧 DDL 写的是 `fact_store_*`。本次按 DDL 用 `fact_store_*`，原始表沿用 `store_raw_data_snapshot`。
- 旧 `store_raw_data_snapshot` 的 CHECK 约束和列注释不一致，见上文。
